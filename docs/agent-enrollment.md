# Agent identity enrollment and request-key contract

Contract identifier: `agent-enrollment/1`.

Status: **PROPOSED**. This document defines a future Keyvault contract. It is not an installed interface or permission to register an account, create a key, or sign. Native custody, accepted-card resolution, implementation, qualification, and adoption remain separate gates.

## Scope

This contract covers an owner-created agent identity, its homeserver account, and the identity's Keyvault-held request key. The request key is a per-identity secp256k1 BIP-340 key for the separately specified typed request operations. It is distinct from the standalone Nostr family, owner keys, child-issuer keys, Namecoin keys, and Matrix end-to-end encryption keys.

This proposed contract does not generalize custody decisions across deployments. The administrative route, account-token custody, and session policy below apply only to the deployment named in the owners' decision of 2026-11-19. Other homeservers require their own owner decision and acceptance. The dated decision and pinned Link decision 0001 are listed under [Sources](#sources); the immutable Link record of the custody decision is pending. Until the deployment-specific sources and route mechanism are accepted, this document remains **PROPOSED**, and registration refuses before reservation and network submission.

The owner alone creates the logical agent identity. A registration operation may run only for an agent with an accepted Pulse card and under the exact identity name selected for that card. For the deployment named in the owners' decision of 2026-11-19, the homeserver account is registered through its system administrator's administrative route; it does not use the owner's account token. Keyvault holds the resulting account token. This enrollment contract does not return it to an agent. Use or release after enrollment is outside this contract and refuses until a separate accepted contract defines it. Each agent can use only its own request key; private key material remains in Keyvault.

## Process and credential boundary

The owning Keyvault custody executable performs the homeserver registration request and native request-key creation within the same process. The new account token passes directly from the registration response to Keyvault's protected custody path in that process. It is stored as a Keyvault secret for the exact account and is not placed in an agent process, IPC request or response, CLI output, argument, environment, prompt, room, log, public record, journal, file outside Keyvault custody, client-library session or credential cache, password custody, crash report, or hash preimage of public data.

The enrollment hook is an IPC client. It supplies no registration credential and receives neither the new account token nor private key material. Any process other than the custody executable, local or remote, that performs registration and relays the token to Keyvault is refused. A two-process design requires a separately accepted authenticated secret-channel contract before implementation.

For the deployment named in the owners' decision of 2026-11-19, the custody executable sends the registration request itself over TLS that authenticates the selected homeserver's administrative route, and receives the response in that process. The mechanism that authorizes this Keyvault request (B2) is not yet named and accepted. Account creation is permitted only through one of two forms under this contract: a create-only route that refuses existing user IDs without logging in to, resetting, or modifying the existing account; or an authenticated response that states this request created the account. A route that creates on first login and logs in thereafter cannot distinguish creation from an existing account and is not acceptable without that authenticated creation statement. Any credential the custody executable presents to the route is a Keyvault secret protected under the same item ACL as the account token; it appears in no IPC, argument, environment, log, or file. Until the route mechanism is named and accepted, registration refuses before reservation and network submission. The system administrator's administrative credential remains with the route and is never returned to the custody executable. The request carries no owner or administrator token. Neither credential is part of the public Keyvault record.

## Accepted identity binding

Before any registration or key effect, the operation is bound to one exact accepted card revision and one exact member identity. The accepted card revision, logical member, selected connection/server, full name, compact Matrix ID, and identity reservation must agree. Names are compared byte-for-byte; there is no alias, punctuation normalization, fallback domain, or name selection from CLI flags.

The member's exact full name must also equal, byte-for-byte, the identity returned by the H1 latch for the consumer. A synthetic H1 name (`syn1:` plus a hexadecimal digest) cannot equal a Pulse full name, so this contract requires explicit H1 selection whose opaque name is the full name. The reservation records that exact origin and consumer binding. A different identity or origin refuses before reservation and network submission. Keyvault writes no H1 record.

New names follow the owner-selected Pulse naming rule. From one reserved `(zone, product, project, role, star)` identity, the selected name pair is:

```text
full name:  <role-code>-<star>.<project>.<product>.<zone>
Matrix ID:  @<project>.<role-code>-<star>:<zone>
```

The v2 naming amendment and its card/resolver representation must be accepted before this route can use them. A syntactic name, desired card entry, local Pulse view, or formatted MXID is not itself an accepted reservation, proof of account existence, or operation authority.

Pulse is a read-only projection of selected card bytes. Its local caller value is unverified, and its source freshness is unknown. The custody operation therefore pins the accepted card digest and obtains the accepted identity binding from the authoritative card and reservation route. Pulse output may select and display the member; it cannot by itself establish card acceptance, current appointment, authenticated caller, account registration, or authority to perform an operation.

During initial validation, an unaccepted card revision, stale or unavailable digest, absent or ambiguous member, name or intended-destination mismatch, or different selected server refuses before the operation writes a reservation or causes a remote or native effect. If identity binding fails at a later recheck, the applicable barrier below stops later effects; a registration request already sent remains disclosed and is not undone.

## Keyvault native operation authorization

Use one predicate, **Keyvault native operation authorization**, for the complete native admission decision. It is true only when all of these facts pass in an admission check before any reservation or journal entry and are re-evaluated in full immediately before every registration submission, before account-token custody, and immediately before native create:

1. Native code admission is defined and passes: the operating system has authenticated the exact signed Keyvault custody executable against the currently protected code requirement, and the matched native pair is qualified for this operation. Undefined or failed admission refuses before reservation and journal entry.
2. A current, finite authorization issued by an owner's act (KEY-MAP K3), given at an OWNER-SITTING route or signed by an owner key that Keyvault verifies against its protected owner pin, permits exactly this registration-and-create operation for the bound identity, homeserver, intended destination (identity and generation), session policy, and public write set. Local eligibility is checked before reservation; remote creation evidence is available only after submission. A manager, agent, run, enrollment hook, session grant, or earlier authorization cannot issue, renew, widen, or transfer it.
3. The authorization's accepted card digest, member identity, exact full name, compact Matrix ID, server, and intended reservation identity and destination match the current selected inputs.
4. The explicit session policy is present, current, and satisfied.

Neither a code signature alone nor a Pulse value, name, environment variable, process ancestry, room membership, token possession, public metadata, general session grant, or agent-session action supplies this authorization. This contract does not isolate malicious processes under the same operating-system user: such a process may drive another identity's genuinely allowed client. This contract makes no same-user principal-isolation claim.

### Required session policy

The session policy must explicitly state the owner-presence rule and the scope in which it applies. For this request-key family, per-key owner presence may be omitted only after an owner-sitting deployment explicitly admits the finite Keyvault management policy for this exact create/use scope. That policy does not extend to owner keys or any other key family. Missing, unknown, expired, or mismatched policy refuses before reservation and the registration request. No default or inferred policy is allowed.

## Fresh destination and public writes

Local eligibility is checked before reservation: the selected identity/generation slot is unused, and there is no pending or unresolved earlier enrollment for that identity. The operation's own reservation is part of this transaction and does not count as an earlier reservation or invalidate local eligibility. A reservation or incomplete transaction from an earlier or different operation does refuse. The absence of a local record is not evidence that the homeserver account is unregistered.

Remote creation evidence becomes available only after submission. A successful result from the accepted create-only route establishes creation under its accepted semantics that refuse existing IDs, or an authenticated response may state that this request created the bound account. An explicit existing-account refusal is a known failed registration, not evidence of freshness; the operation cannot adopt that account. Existing homeserver accounts, Keyvault records, prior reservations, or incomplete earlier transactions are not eligible destinations. The operation cannot overwrite them, rotate them, or create a replacement automatically.

The operation's finite public write set is limited to the selected Keyvault record's public metadata projection:

| Public field | Bound value |
| --- | --- |
| Selection | Request-key family, purpose, and explicit generation |
| Identity | Exact accepted full name, compact Matrix ID, and selected homeserver name |
| Revision | The record's assigned revision for this generation |
| Public key | The x-only public key corresponding to the private request key |

These values are published only in the public metadata projection of the selected Keyvault record. No other record, room, message, homeserver profile, or public registry is a publication destination in this contract. The account token, registration credentials, private key, seed, or secret-derived value is never public metadata. Any additional field or destination requires a revised finite write set and renewed agreement.

## Transaction order and uncertain outcomes

Before writing any reservation or journal entry, the custody executable validates native code admission, the accepted identity binding, the complete Keyvault native operation authorization for the intended locally eligible destination, session policy, unused identity/generation slot, absence of pending or unresolved earlier enrollment, and the complete write set. If any initial check fails, including when native code admission is undefined or fails, it refuses without writing a reservation or journal entry and without a remote or native effect. Only after every initial check passes does it durably record a nonsecret reservation for the original operation identity and immutable intended destination. The reservation binds that destination but does not prove that its homeserver account is unregistered; the accepted route later supplies remote creation evidence.

Immediately before every initial or resumed registration submission, the executable re-evaluates the complete authorization facts 1 to 4 and the accepted identity binding, including the H1 identity, origin, and consumer, as well as the actual peer, original principal or intent, session policy, caps, and write set. A failed pre-submission recheck sends zero requests, retains the existing reservation, and leaves the enrollment incomplete and blocked without token custody, key creation, or publication. After a valid registration response, it rechecks the complete authorization facts 1 to 4 and identity binding, including the H1 join, applicable peer, original principal or intent, operation-authorization expiry or revocation, session-policy expiry, caps, and write set before account-token custody and again immediately before native create. A failed post-submission check prevents every later effect and leaves the enrollment incomplete and blocked; it does not undo or conceal a registration request already sent.

The executable performs one registration through the administrative route after its mechanism is named and accepted under B2. Before protected custody, the response must contain an access token and the exact bound compact Matrix ID from the authenticated selected server. A successful response from the accepted create-only route establishes remote creation under its accepted semantics that refuse existing IDs; alternatively, an authenticated response may state that this request created the account. An explicit existing-account refusal is a known failed registration, not creation evidence, and the account cannot be adopted. The absence of a local record is not evidence that the homeserver account is unregistered. A missing, malformed, mismatched, other-user, other-server, or otherwise inconclusive response is an **UNKNOWN** registration result: no account token is committed to protected custody, no request key is created, and the destination remains blocked. On a valid response, the executable creates the selected Keyvault request-key record. It publishes public metadata only after an authenticated, complete committed receipt exists for this exact original operation; an absent, incomplete, or different-operation receipt permits no publication. An exact replay returns the retained public result without a second registration, key creation, or write. No other account or generation may be selected implicitly. The enrollment hook receives only the public metadata projection. Private signing is available only to the bound agent through a separate accepted request-key use path.

An unknown registration result, lost token, interrupted key creation, or uncertain public-record write leaves the enrollment incomplete and its destination blocked. The vault does not retry registration, adopt an account, create a replacement key, rotate the generation, or claim that no remote effect happened. Only an owner's recorded act, given at an OWNER-SITTING route or signed by an owner key that Keyvault verifies against its protected owner pin, closes a blocked enrollment. A later registration is a new operation with a new owner-issued authorization and fresh destination; an unsettled reconciliation remains blocked.

## Contract controls

| Valid control | Required refusal or limit |
| --- | --- |
| Owner-issued authorization binds the exact operation, identity, server, generation, session policy, destination, and write set | A manager, agent, run, hook, session grant, earlier authorization, or authorization for another identity refuses before reservation and network submission; no remote or native effect follows |
| One accepted card digest, unique reserved member identity, matching server, current authorization, locally eligible identity/generation slot, and bound intended destination | A stale or unaccepted card, ambiguous member, changed name or server, pre-existing reservation, or substituted digest refuses before network submission; no registration request is sent. The operation's own reservation does not invalidate the slot; remote creation evidence is established only after submission |
| At reservation, the accepted card revision, exact member identity and full name, compact Matrix ID, selected server, and H1 latch identity, origin, and consumer match byte-for-byte | An unaccepted or superseded card, absent or ambiguous member, renamed identity, or changed H1 identity, origin, or consumer refuses before reservation; no remote or native effect follows; Keyvault writes no H1 record |
| Defined native code-admission policy, exact signed custody executable authenticated under its protected requirement, and qualified matched pair | Undefined or failed admission, wrong, unsigned, rebuilt, or unqualified executable refuses before reservation and journal entry, with no remote or native effect. A later failed recheck retains the existing reservation and stops the next effect |
| Explicit current session policy admitted for the deployment named in the owners' decision of 2026-11-19 | Missing, unknown, expired, or mismatched policy refuses before reservation and the registration request; no inferred unattended mode, and it never replaces the owner-issued operation authorization |
| The custody executable uses TLS to authenticate the selected administrative route, and both the route and its account-creation behavior are named and accepted for the deployment named in the owners' decision | An unauthenticated or different endpoint, unnamed or unaccepted B2 mechanism, or local/remote relaying process refuses before reservation and network submission |
| Account creation uses a create-only route or an authenticated response that states this request created the account | An explicit existing-account refusal is a known failed registration; an inconclusive result is UNKNOWN. No token enters custody, no key is created, and the destination stays blocked. A route that logs in to an existing account without authenticated creation evidence is not accepted |
| The authenticated selected server returns a token and the exact bound compact Matrix ID, with accepted evidence that this operation created the account | Missing, malformed, mismatched, other-user, other-server, or creation-evidence-free response is UNKNOWN; an explicit existing-account refusal is a known failure. No token is committed, no key is created, and the destination stays blocked |
| Complete authorization facts 1 to 4 and the exact accepted identity binding, including the H1 join, are rechecked before every initial or resumed registration submission; peer, principal or intent, session policy, caps, and write set still match; a passing check permits one request for the reserved identity/generation | An unaccepted or superseded card, absent or ambiguous member, renamed identity, changed H1 identity/origin/consumer, expired, revoked, or non-matching authorization; missing, unknown, expired, or mismatched policy; failed code admission; changed write set; changed peer/principal/intent; exceeded cap; or any other failed recheck refuses before submission; zero requests are sent, the existing reservation is retained, no later custody, key creation, or publication occurs, and the enrollment remains incomplete and blocked |
| Complete authorization facts 1 to 4, the exact accepted identity binding including the H1 join, current peer, original principal or intent, operation-authorization expiry or revocation status, session-policy expiry, caps, and write set are rechecked before account-token custody | Any failed post-submission recheck prevents token custody, key creation, and publication; the enrollment stays incomplete and blocked, and the already-sent registration request is not undone or concealed |
| Complete authorization facts 1 to 4, the exact accepted identity binding including the H1 join, current peer, original principal or intent, operation-authorization expiry or revocation status, session-policy expiry, caps, and write set are rechecked immediately before native create | Any failed recheck prevents key creation and publication; the enrollment stays incomplete and blocked, and any earlier registration or token custody is not undone or concealed |
| One locally eligible identity/generation and one fixed public write set | An existing account or Keyvault key, prior reservation, pending or unresolved earlier enrollment, changed generation, extra public field, or different destination refuses without overwrite or automatic recovery; existing state remains unchanged |
| One incomplete enrollment per destination, excluding the current operation's own reservation | A second enrollment for the same identity or destination refuses before reservation and network submission; the first enrollment remains unchanged and the current operation's reservation does not invalidate itself |
| The exact original operation has an authenticated complete committed receipt before public metadata is written | Missing, incomplete, or different-operation receipt permits no publication; an exact replay returns the retained public result without a second effect |
| Only public metadata is returned to the hook; the bound agent uses a separate accepted request-key path | An inbound IPC request in which the hook supplies a registration credential, account token, or other secret field is refused before reservation and network submission; the supplied value is necessarily present in that inbound request, but is neither used nor stored. This known pre-reservation refusal writes no reservation or journal entry, leaves existing enrollment state unchanged, sends no request, and is not UNKNOWN or blocked. If a token or credential is detected later, after reservation, in an outgoing hook response or another output/persisted sink, no later custody, key creation, or publication follows; the result is UNKNOWN and the destination remains blocked. A private key, seed, account token, administrative credential, or another agent's key is never exported. The nonappearance guarantee covers outgoing IPC responses, arguments, environment, logs, rooms, prompts, generic result objects, journal, operation-written files, client cache, fallback credential cache, password custody, crash reports, and public-data hash preimages; it does not cover the refused inbound IPC request itself |
| An owner's recorded act, given at an OWNER-SITTING route or signed by an owner key verified against the protected owner pin, closes a blocked enrollment; a later registration is a new operation with a new owner-issued authorization and fresh destination | Timeout, agent/run/manager action, or unsettled reconciliation leaves it incomplete and blocked; no retry, replacement, rotation, or inference that the remote account was not created |

The contract permits source preparation against **PROPOSED** text only. It does not implement account registration or request-key issuance, qualify native code admission or token storage, prove live Pulse acceptance, or claim an attended or unattended operation has occurred.
